# Preface

Every project that grows ends up facing the same questions: what has changed since the last version, who made that change and why, how to go back when something breaks, and how several people can work at the same time without stepping on each other's toes. Git and GitHub answer all of them, and that is why they have become essential tools.

**Git** is a version control system: it saves each state of a project as a snapshot with its author, its date and an explanation of the change, so the full history is always at hand. With it we can compare two versions line by line, recover any earlier point, open parallel lines of work (branches) to try out ideas without risk and merge them later, and mark the versions we publish. What's more, every copy of the project carries the whole history, so you can work offline and no server failure puts the work at risk. Linus Torvalds created it in 2005 to coordinate the development of the Linux kernel, one of the projects with the most contributors in the world, and today it is the standard both for people who work alone and for the largest technology companies.

**GitHub** takes Git to the cloud and turns it into a collaboration platform. _Pull requests_ let you propose a change, review it, comment on it and accept or reject it before it reaches the main version; _issues_ organize tasks and bugs; _forks_ let anyone contribute to someone else's project; and GitHub Actions automates the repetitive work, such as checking every change, generating documents or publishing a release or a website. This model has made free software possible as we know it, with projects where thousands of people who have never met work together, and today more than a hundred million people use it.

Git was born for software, but it doesn't care about programs: it cares about text files. That is why it is just as useful for anyone whose work can be written in plain text, whether notes, documentation, articles, a thesis, a book or a website. Anyone who writes in Markdown, LaTeX or any other text format can see exactly what has changed between two versions, work with other people on the same document without losing anything and publish the result automatically. With a Word document, on the other hand, Git can only store copies, without explaining what has changed between them.

This course grew out of that idea: to be a guide to Git and GitHub accessible to everyone, not only to those who program. So, instead of illustrating the concepts with an application, it applies them all to a single practical example: a Markdown book about Git, the _Git Handbook_, which we build module by module and which a script converts to Word, PDF and HTML. This way we will see every command in a real, useful case that requires no programming knowledge, and by the end you will have a complete project on GitHub, with its history, its versions and its automatic publishing.

This way of working with text is even more valuable today, with artificial intelligence. Many of our interactions with it are pure text and, when we work with an agent, whether to write code or prose, we are really collaborating with it: the agent proposes changes to our files and we have to review them effectively, decide which ones to accept and which to reject, understand how they came about and undo them if something goes wrong. That is exactly what Git and GitHub teach us to do: every change is recorded, compared with the previous version, reviewed in a branch or a pull request before it is integrated and, if we are not convinced, discarded without touching the good work.

Being accessible doesn't mean the course is superficial. It covers Git and GitHub completely and rigorously: commits and the staging area, traveling through history with `reset`, `revert` and `reflog`, branches, merges and conflicts, remote repositories, forks and pull requests, workflows, `cherry-pick` and `rebase`, and continuous integration and deployment with GitHub Actions. If you work in software development, you will find here everything you need to master these tools without missing a thing, because the example is a book, but the commands, the workflows and the pipelines are the same as in any software project.

## How the course is organized

The course moves from the basics to the advanced topics, and each module builds on the previous ones:

- [Module 1](01-introduction-and-first-steps.md) introduces Git and GitHub, explains how to install Git and gets the terminal ready.
- Modules [2](02-local-version-control.md), [3](03-time-travel-and-save-points.md) and [4](04-branching-and-merging.md) work only locally: commits, undoing changes, time travel, tags, branches and merges.
- Modules [5](05-github-and-remote-work.md) and [6](06-collaboration-and-open-source.md) upload the book to GitHub and teach you to collaborate with remote repositories, forks and pull requests.
- [Module 7](07-workflows-and-advanced-commands.md) presents workflows and advanced commands.
- [Module 8](08-github-actions.md) automates checking and publishing the book with GitHub Actions.
- The appendices cover the [tools in the example that are not part of Git](09-appendix-example-dependencies.md) (Pandoc and Typst) and the [references cited throughout the course](10-appendix-useful-references.md).

Every demonstration follows the same path: first we explain what situation we are going to set up and why, then we build the scenario, look at the state of the history in a diagram (its legend is explained in section 2.4) and, finally, we solve the problem with the right command. Some sections end with an _Advanced_ subsection, which you can skip on a first reading without losing the thread. The commands are written for bash, which on Windows is used through Git Bash, and there is no need to memorize them: in section 1.2 we present the references worth keeping at hand.

Whether you write code or prose, I invite you to open the terminal and join me from the first commit to the automatic publishing of the book. By the end of the journey, Git and GitHub will no longer be programmers' tools but your way of working, and you will wonder how you ever managed without them.
