# Prefacio

Todo proyecto que crece acaba enfrentándose a las mismas preguntas: qué ha cambiado desde la última versión, quién hizo ese cambio y por qué, cómo volver atrás cuando algo se estropea y cómo pueden trabajar varias personas a la vez sin pisarse. Git y GitHub responden a todas ellas, y por eso se han convertido en herramientas imprescindibles.

**Git** es un sistema de control de versiones: guarda cada estado de un proyecto como una instantánea con su autor, su fecha y una explicación del cambio, de modo que el historial completo queda siempre a mano. Con él podemos comparar dos versiones línea a línea, recuperar cualquier punto anterior, abrir líneas de trabajo paralelas (las ramas) para probar ideas sin riesgo y fusionarlas después, y marcar las versiones que publicamos. Además, cada copia del proyecto lleva el historial entero, así que se puede trabajar sin conexión y ningún fallo de un servidor pone en peligro el trabajo. Linus Torvalds lo creó en 2005 para coordinar el desarrollo del núcleo Linux, uno de los proyectos con más colaboradores del mundo, y hoy es el estándar tanto para quien trabaja solo como para las grandes empresas tecnológicas.

**GitHub** lleva Git a la nube y lo convierte en una plataforma de colaboración. Las _pull requests_ permiten proponer un cambio, revisarlo, comentarlo y aceptarlo o rechazarlo antes de que llegue a la versión principal; los _issues_ organizan las tareas y las incidencias; los _forks_ permiten que cualquiera contribuya a un proyecto ajeno; y GitHub Actions automatiza lo repetitivo, como revisar cada cambio, generar documentos o publicar una versión o una web. Este modelo ha hecho posible el software libre tal como lo conocemos, con proyectos en los que colaboran miles de personas que nunca se han visto, y hoy lo usan más de cien millones de personas.

Git nació para el software, pero no entiende de programas: entiende de ficheros de texto. Por eso es igual de útil para cualquier persona cuyo trabajo se pueda escribir en texto plano, ya sean apuntes, documentación, artículos, una tesis, un libro o una web. Quien escribe en Markdown, LaTeX o cualquier otro formato de texto puede ver exactamente qué ha cambiado entre dos versiones, trabajar con otras personas sobre el mismo documento sin perder nada y publicar el resultado de forma automática. Con un documento de Word, en cambio, Git sólo puede guardar copias, sin explicar qué ha cambiado entre ellas.

Este curso nace de esa idea: ser una guía de Git y GitHub accesible para todos los públicos, no sólo para quienes programan. Por eso, en lugar de ilustrar los conceptos con una aplicación, los aplica todos a un mismo ejemplo práctico: un libro en Markdown sobre Git, el _Manual de Git_, que vamos construyendo módulo a módulo y que un script convierte a Word, PDF y HTML. De este modo veremos cada comando en un caso real y útil en el que no hace falta saber programar, y al terminar tendrás en GitHub un proyecto completo, con su historial, sus versiones y su publicación automática.

Esta forma de trabajar con texto es todavía más valiosa hoy, con la inteligencia artificial. Buena parte de nuestras interacciones con ella son puro texto y, cuando trabajamos con un agente, ya sea para programar o para redactar, en realidad colaboramos con él: el agente propone cambios en nuestros ficheros y nosotros tenemos que revisarlos con eficacia, decidir cuáles aceptamos y cuáles rechazamos, entender cómo se ha llegado a ellos y deshacerlos si algo sale mal. Eso es exactamente lo que Git y GitHub nos enseñan a hacer: cada cambio queda registrado, se compara con la versión anterior, se revisa en una rama o en una pull request antes de integrarlo y, si no nos convence, se descarta sin tocar el trabajo bueno.

Que el curso sea accesible no significa que sea superficial. Cubre Git y GitHub de forma completa y rigurosa: los commits y el área de preparación, los viajes por el historial con `reset`, `revert` y `reflog`, las ramas, las fusiones y los conflictos, los repositorios remotos, los forks y las pull requests, los flujos de trabajo, `cherry-pick` y `rebase`, y la integración y el despliegue continuos con GitHub Actions. Si te dedicas al desarrollo de software, encontrarás aquí todo lo que necesitas para dominar estas herramientas sin echar nada de menos, porque el ejemplo es un libro, pero los comandos, los flujos y los workflows son los mismos que en cualquier proyecto de software.

## Cómo está organizado el curso

El curso avanza de lo básico a lo avanzado, y cada módulo se apoya en los anteriores:

- El [módulo 1](01-introducción-y-primeros-pasos.md) presenta Git y GitHub, explica cómo instalar Git y prepara la terminal.
- Los módulos [2](02-control-de-versiones-en-local.md), [3](03-viajes-en-el-tiempo-y-puntos-de-guardado.md) y [4](04-ramificación-y-fusiones.md) trabajan sólo en local: commits, deshacer cambios, viajes en el tiempo, etiquetas, ramas y fusiones.
- Los módulos [5](05-github-y-trabajo-remoto.md) y [6](06-trabajo-colaborativo-y-open-source.md) suben el libro a GitHub y enseñan a colaborar con repositorios remotos, forks y pull requests.
- El [módulo 7](07-flujos-de-trabajo-y-comandos-avanzados.md) presenta los flujos de trabajo y los comandos avanzados.
- El [módulo 8](08-github-actions.md) automatiza la revisión y la publicación del libro con GitHub Actions.
- Los anexos recogen las [herramientas del ejemplo que no son de Git](09-anexo-dependencias-de-los-ejemplos.md) (Pandoc y Typst) y las [referencias citadas a lo largo del curso](10-anexo-referencias-útiles.md).

Cada demostración sigue el mismo camino: primero planteamos qué situación vamos a preparar y para qué, después construimos el escenario, miramos el estado del historial con un diagrama (su leyenda se explica en el apartado 2.4) y, por último, resolvemos el problema con el comando que toca. Algunos apartados terminan con una subsección _Avanzado_, que puedes saltarte en una primera lectura sin perder el hilo. Los comandos se escriben para bash, que en Windows se usa con Git Bash, y no hace falta memorizarlos: en el apartado 1.2 presentamos las referencias que conviene tener a mano.

Tanto si escribes código como si escribes textos, te invito a abrir la terminal y acompañarme desde el primer commit hasta la publicación automática del libro. Al final del camino, Git y GitHub habrán dejado de ser herramientas de programadores para convertirse en tu forma de trabajar, y te preguntarás cómo te las arreglabas antes sin ellas.
